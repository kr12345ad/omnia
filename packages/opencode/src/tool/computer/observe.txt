Summarize the current computer state with enough detail to act without guessing.

Returns the observation id, the applications and windows present, the element
that currently holds keyboard focus, and a compact list of controls. Every
control line includes its role, name, stable ref, exact screen pixel center,
current value when it has one, its states (enabled, focused, checked, expanded,
and so on), and the actions it supports.

Reading one line looks like this:

  - button "Save" at 412,88 ref=atspi:3 [enabled] actions=click
  - textbox "Name" at 200,140 ref=atspi:4 value="Ada" [enabled, focused] actions=set-text
  - window "Budget 2026 (LibreOffice Calc)" at 960,540 ref=atspi:1

Windows are grouped first, then the focused element, then up to `limit`
controls (default 120, max 1000). When the list is cut short the output says
so and names how many more exist; that is a signal to narrow, not to ask for
a bigger dump.

Use it to orient yourself at the start of a task and after any change. If a
control you need is not listed, narrow with computer_find instead of asking for
a bigger dump, and use computer_inspect for full detail on one control.

Refs are stable identifiers for accessible controls and are the preferred way
to act: pass a control's ref as the target of computer_act. No vision model is
needed to act on accessible controls; coordinates are a fallback only for
canvas or image surfaces that expose no ref. For the full structured JSON of
a snapshot (refs, roles, values, states, and bounds for every control),
use computer_snapshot instead of a bigger text dump.

Parameters:

- applicationId (or app): restrict to one application, for example "soffice".
  Omit for everything visible. Prefer this over reading the whole desktop
  when you know which app owns the task.
- window: restrict further to one window by title or app fragment, for
  example "Default Project". Combine with the application when several
  windows share a title.
- limit: maximum controls in the text summary (1-1000). Keep it small when
  scouting and raise it only when the target is known to be further down.

Warnings at the end of the output are load-bearing: a truncated or degraded
tree means some controls are invisible to the runtime. Trust only what is
listed. After any click, keypress, dialog, or window change the previous
observation is stale: observe again before the next act.
